AIOS · mini-aios

Bluetooth & Account Pairing Architecture

End-to-end map of how an offline AIOS box gets onto Wi‑Fi via BLE, then binds to a user account through LAN + aios-cloud, and stays reachable via relay and Cloudflare Tunnel.

Overview Two pipelines BLE Wi‑Fi Account pairing Tokens Runtime States Storyboard

1. System overview

Three actors. The phone talks to the box over BLE (offline) and LAN HTTP (online). The box talks to cloud over HTTPS (claim) and WSS (relay). Off-LAN clients reach the box through a per-device Cloudflare tunnel.

2. Two pipelines — do not conflate

BLE does not bond, pair, or exchange account secrets. Account binding is a separate LAN/cloud handshake that yields local_token + device_token.
Pipeline Channel Purpose When
A — BLE Wi‑Fi provisioning Bluetooth LE GATT + app-layer crypto Get an offline box onto Wi‑Fi Boot, no usable LAN
B — Account pairing mDNS + LAN HTTP + cloud HTTPS/WSS + tunnel Bind box to a user account After box is online

3. Pipeline A — BLE Wi‑Fi provisioning

Transport is plain BLE (no OS bonding). Security is entirely in the payload: ephemeral X25519 ECDH → HKDF → AES-256-GCM with the challenge as AAD (anti-replay). 

sequenceDiagram
  autonumber
  participant Phone as Phone
  participant BLE as Box BLE GATT
  participant NM as nmcli
  participant Main as main.py

  Main->>BLE: offline boot → advertise aios-id[:8]
  Phone->>BLE: Connect plain BLE no bonding
  Phone->>BLE: Read PUBKEY ephemeral X25519
  Phone->>BLE: Read CHALLENGE fresh nonce
  Note over Phone: ECDH → HKDF → AES-GCM
AAD = challenge
  Phone->>BLE: Write CREDS phonePub + blob
  BLE-->>Phone: STATUS credentials_received
  BLE->>NM: wifi connect ssid password
  alt success
    BLE-->>Phone: STATUS connecting → connected
    BLE->>Main: tear down BLE → start FastAPI
  else failure
    BLE-->>Phone: STATUS failed reason
    Note over BLE: stay advertising for retry
  end

GATT surface

Service  7A71E000-1111-2222-3333-123456789ABC
├── CREDS     …E001  write   ← {"phonePub":"<hex>","blob":"<base64>"}
├── STATUS    …E002  notify → credentials_received | connecting | connected | failed:<reason>
├── PUBKEY    …E003  read   → box ephemeral X25519 pubkey (hex)
└── CHALLENGE …E004  read   → fresh 16-byte nonce (hex), regenerated every read

Crypto (v2)

flowchart LR
  P[Phone] -->|1. read PUBKEY + CHALLENGE| B[Box]
  P -->|2. X25519 ECDH + HKDF info=aios-provisioning-v2| K[32-byte session key]
  K -->|3. AES-256-GCM seal ssid/password| Blob["blob = nonce12 ‖ ct ‖ tag16"]
  P -->|4. write CREDS| B
  B -->|same ECDH/HKDF → decrypt → nmcli| WiFi[Join Wi‑Fi]

Wire blob: base64(nonce[12] ‖ ciphertext ‖ tag[16]). Plaintext: {"ssid":"…","password":"…"}. Modules: main.py → server/provisioning.py → server/provisioning_crypto.py.

4. Pipeline B — Account pairing

The app never sends cloud credentials to the box. It only hands a short-lived pairing code over the LAN; the box redeems it with the cloud and mints its own local_token for future Bearer auth. 

sequenceDiagram
  autonumber
  participant App as Phone / Desktop
  participant Cloud as aios-cloud
  participant Box as AIOS Box
  participant CF as Cloudflare

  Note over Box: Online: mDNS + GET /device/info
  App->>Cloud: Auth + request pairing_code
  Cloud-->>App: short-lived pairing_code
  App->>Box: Discover mDNS or cloud lan_ip
  App->>Box: POST /pair pairing_code
  Box->>Cloud: POST /device/claim/complete
  Cloud-->>Box: device_token user slug connector_token hostname
  Note over Box: mint local_token · save device_link · start cloudflared
  Box-->>App: local_token device_id slug hostname
  App->>App: Store local_token
  Box->>Cloud: WSS /ws/device?token=device_token
  Box->>CF: cloudflared tunnel run
  Note over App,Box: Bearer local_token over LAN or public hostname

Key APIs

StepDirectionEndpointPayload
Discover App → Box mDNS _aios._tcp / GET /device/info {device_id, name, paired, slug}
Redeem App → Box POST /pair {pairing_code}
Claim Box → Cloud POST /device/claim/complete {device_id, pairing_code}
Claim OK Cloud → Box 200 device_token, user, slug, connector_token?, hostname?
Pair OK Box → App 200 local_token, device_id, slug, hostname, …
Relay Box → Cloud WSS /ws/device?token=… heartbeats + commands
Tunnel Box → CF cloudflared public hostname → :8765

5. Tokens & identity

Three auth planes: BLE app crypto (Wi‑Fi only), local_token (app↔box HTTP), device_token (box↔cloud WSS).

ArtifactWho mintsLifetimeUsed for
device_id Box (SQLite) Forever BLE name, mDNS TXT, claim
pairing_code Cloud Short / one-shot Bind box ↔ user
device_token Cloud Long-lived Box → cloud WSS
local_token Box Until unpair App → box HTTP Bearer
connector_token Cloud Long-lived cloudflared
BLE X25519 keys Ephemeral One session Wi‑Fi cred encryption only

6. Post-pair runtime topology

Same local_token works on LAN and through the tunnel. Cloud can still reach the box via the outbound WSS relay (e.g. remote unpair) without the LAN token.

7. Account pairing state machine

stateDiagram-v2
  [*] --> UNPAIRED
  UNPAIRED --> PAIRING: POST /pair
  PAIRING --> PAIRED: claim OK · mint local_token · tunnel + WSS
  PAIRING --> UNPAIRED: claim failed
  PAIRED --> UNPAIRED: POST /unpair or relay unpair
Unpaired

Public surface

device_link = None. Relay idle-polls. /device/info.paired = false. POST /pair allowed.

Paired

Guarded surface

Bearer local_token required. cloudflared up. Relay connected with device_token.

8. Boot → pair storyboard

Offline → online → claimed. BLE gets you on the network; pairing code binds ownership; tokens unlock ongoing control.

flowchart TD
  A["① Fresh box powers on, no Wi‑Fi"] --> B["② BLE advertises aios-id[:8]"]
